## 决策结论

`accept`

接受“SSD/NVMe 热层 + HDD 冷归档 + 独立备份层”作为个人智库的默认存储架构。

1. **热层**保存 PostgreSQL `PGDATA`、WAL、B-tree/GIN 索引、pgvector/HNSW 索引、实体与事件关系、任务队列、缓存和需要频繁更新的运行状态。
2. **冷归档层**保存原始网页、WARC、PDF、图片、音视频、OCR 中间物、历史快照、可重建的模型原始输出和批量导出。
3. **长期记忆不等于冷藏全部数据**。历史事件的向量、实体、时间、Claim、证据定位与归档指针继续留在热层；系统先在热层唤醒候选，只有需要核对原文时才读取 HDD。
4. **备份层必须是另一块物理介质或另一台设备**。同一 HDD 上的第二份文件不是灾难恢复备份。
5. 初期如果只有机械盘，可以用 `storage_profile=hdd_mvp` 完成采集和模型校准，但所得延迟不能作为生产性能基线，也不得据此授权多 Agent 并发。

本卡只接受存储架构，不代表 DeepSeek V4 Flash 已通过能力门禁，也不改变 EX-JX32 的冻结样本与评分规则。

## 这个节点是什么

个人智库既要保存大量原始材料，又要让 Agent 快速找回几个月前的相关事件。前者需要便宜的大容量，后者需要低延迟的随机读取。把所有内容都放 SSD 成本偏高，把数据库和向量索引都放机械盘则会在索引未命中内存、多 Agent 并发和 HNSW 构建时显著变慢。

因此将“记忆目录”和“记忆索引”分离：机械盘负责保存原件，SSD 负责保存可检索的记忆结构。这与图书馆把书存入书库、把目录放在快速检索系统中的做法相同。

## 相比上一个节点改变了什么

- 原方向只规定原始新闻和大型结果不进入量化研究库，没有决定独立智库项目内部如何分层存储。
- 现在明确 PostgreSQL 与向量索引默认属于热层，不能因为机械盘容量大就把整个在线数据库放入冷归档层。
- 现在明确历史 B 事件即使原文已归档，其向量、实体关系和证据指针仍应可被当前 A 事件快速召回。
- 现在引入三个逻辑根，执行项目不得在数据库中固化个人绝对路径：`THINKTANK_HOT_ROOT`、`THINKTANK_ARCHIVE_ROOT`、`THINKTANK_BACKUP_ROOT`。
- 现在明确短网页和小型 JSON 不应永久采用“一条新闻一个小文件”的无限扩张布局。

## 数据放置契约

| 数据 | 默认层级 | 说明 |
| --- | --- | --- |
| PostgreSQL `PGDATA` 与 WAL | 热层 | 频繁随机读写，不放在网络同步目录 |
| Claim、Event、Entity、时间与来源关系 | 热层 | 是长期记忆的检索骨架 |
| pgvector 向量与 HNSW/IVFFlat 索引 | 热层 | 尽量让活跃索引进入内存，未命中时仍需要 SSD 随机读取 |
| 清洗后的正文 | 热层优先 | 便于全文检索；容量压力出现后才按独立规则迁移 |
| 原始 HTML、WARC、PDF、图片、音视频 | 冷归档层 | 使用内容哈希和稳定归档 URI 定位 |
| OCR 中间文件与可重建模型输出 | 冷归档层 | 设置保留期，禁止无期限重复保存 |
| 数据库导出与灾难恢复备份 | 独立备份层 | 不与唯一原件位于同一物理盘 |

每个归档对象至少登记：`content_sha256`、`storage_uri`、`storage_tier`、`media_type`、`byte_size`、`archived_at`、`verified_at`。应用保存逻辑 URI，不保存某台电脑的固定盘符。

## 小文件与碎片控制

- 文件碎片主要损害机械盘寻道性能，通常不是容量暴涨的主要原因。
- 真正需要重点控制的是百万级小文件的分配单元浪费、NTFS 元数据、重复快照、PostgreSQL 死元组、重复向量和失控日志。
- 短 HTML、纯文本和 JSON 可按来源与日期写入有上限的 WARC 或 `JSONL.zst` 分片；大型 PDF、图片、音视频保留为内容寻址对象。
- 不建立无限增长的单一压缩包；每个分片必须可校验、可索引、可独立恢复。
- HDD 至少保留 20% 可用空间，定期分析碎片；只对机械盘执行合适的碎片整理，不把传统碎片整理策略照搬到 SSD。
- PostgreSQL 保持 autovacuum，监控表与索引膨胀；普通 `VACUUM` 用于复用空间，只有经过维护窗口评估后才使用需要重写和额外空间的操作。

## 支持证据

- PostgreSQL 官方将机械盘列为随机读取成本相对更高的存储；数据库索引与向量检索会产生大量非顺序页访问。[PostgreSQL 查询规划](https://www.postgresql.org/docs/current/runtime-config-query.html)
- pgvector 官方说明 HNSW 的速度与召回较好，但构建较慢、使用更多内存；图结构不能装入 `maintenance_work_mem` 时构建会显著变慢。[pgvector 索引说明](https://github.com/pgvector/pgvector)
- PostgreSQL 不会为每条新闻创建一个操作系统文件，表或索引超过默认 1 GB 后才分段，因此把正文放在数据库中比建立百万个短 JSON 文件更适合在线检索。[PostgreSQL 文件布局](https://www.postgresql.org/docs/current/storage-file-layout.html)
- Microsoft 明确指出非连续文件会降低 HDD 读写性能，完整整理通常需要至少 15% 空闲空间；本卡采用更保守的 20% 运维线。[Microsoft defrag](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/defrag)
- 当前 DeepSeek 探针耗时以模型调用为主，MVP 阶段 HDD 的毫秒级读取不是首要瓶颈；但这个事实不能外推到未来的高并发检索。
- 实际项目验证表明逻辑URI、卷身份、剩余空间、独立备份设备和破坏性迁移守卫可以在没有数据库前自动检查；当前明确停留在`hybrid / provisional`，没有把`exFAT`临时副本伪装成`durable`。
- 双副本隔离恢复表明当前锚不是只有哈希收据：任一副本都能重建控制文件、内容寻址对象和原逻辑URI树，archive与backup的完整内容指纹均为`sha256:129bfc1305b6bbd6c963522e58326179a405bc76de88ac612867563aace9cccc`。

## 反对证据

- 如果数据集和索引长期完全进入内存，机械盘上的数据库可能暂时感觉不到明显变慢。
- 小规模个人系统把所有数据放在一块盘上更简单，冷热迁移会增加配置、校验和恢复复杂度。
- 机械盘顺序写入足以承担新闻抓取与批量归档，全 SSD 并不是功能正确性的前提。
- 当前只有421个去重正文对象、约14.1MB唯一正文的一次双副本恢复证据，没有10万篇规模、并发量、索引尺寸、RTO/RPO和p95延迟数据，无法确定热层容量或冷热迁移阈值。

## 边界

本决策没有选择SSD/HDD品牌、容量、RAID方式、对象存储实现、压缩算法、热数据保留月份或PostgreSQL参数。Windows正式耐久锚只接受NTFS/ReFS，但尚未在两者之间作最终选择；上述项目必须根据执行机器和实际规模单独测量。

本决策也不能证明 PostgreSQL + pgvector 已经是最终长期记忆方案，不能证明 HNSW 一定优于 IVFFlat，更不能证明 DeepSeek V4 Flash 可以写入最终事实库或影响投资决策。

## 后续动作

1. 独立智库执行仓库、三个逻辑根和双盘对象快照已经建立；共享资产继续只写逻辑URI。
2. 只有用户选定空的独立NTFS/ReFS机械盘后，才由C6生成当前/候选新鲜存储证明和冻结计划；用户核对计划并独立建立最长24小时的只复制授权后才运行`copy`。取得`verified_copy`后复用恢复器验收，逻辑根切换另需一次明确批准；不得原地格式化或自动删除`exFAT`源。
3. 迁移后重新生成存储证明和首个`durable`锚；热层空间恢复到20%以上前仍保持`ready_for_production=false`。
4. EX-JX32的30篇校准和EX-JE6T连续采集可以在`hybrid / provisional`下继续，但语料清单必须记录存储状态，保证模型能力与磁盘性能结论不混淆。
5. 在进入10万篇以上语料或两个以上并发Agent前，另开存储基准实验，至少测量全文检索、向量检索、原文回读、批量写入和索引构建的p50/p95。
6. 只有基准实验表明热层容量或成本不合理时，才调整正文、旧向量或索引的放置策略。
