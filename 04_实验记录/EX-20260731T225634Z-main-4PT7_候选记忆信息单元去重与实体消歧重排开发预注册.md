## 1. 新手摘要

BM25已经能把相关历史放进候选列表，但有时会把“同一件事的另一篇官方解读”或“同领域的另一个产品/设施”排在最前。本实验不重做BM25，而是在它之后增加一个独立后处理层。

第一阶段只验证工程契约：可信元数据能排除同一信息单元、折叠重复材料并把显式错产品/错设施降到真正匹配项之后；不可信模型标签不能影响硬排序；后处理绝不能新增候选、恢复未来材料或把候选变成事实。即使全部通过，也只算L1工程证据，不代表真实召回准确率已经改善。

## 2. 假设

在BM25完成时间、版本、复核状态和隔离过滤之后，使用与候选payload绑定、且经过确定性或人工复核的独立元数据，可以通过无训练权重的优先级规则完成三件事：

1. 排除与查询A共享检索侧`information_unit_key`的派生稿；
2. 将同一历史信息单元的多个候选折叠为原始BM25排名最高的一项；
3. 在BM25短名单内，使产品、科研设施等强类型ID明确匹配的候选排在明确冲突项之前。

该层只重排既有候选，不批准关系或事实，不取代高智能模型的因果与关系判断。

## 3. 实验前预测

实现前冻结以下机制夹具和点预测：

| 夹具 | 预期 |
| --- | --- |
| 查询A与候选共享已验证`information_unit_key` | 候选被排除并留下可审计原因 |
| 两个历史候选共享已验证`information_unit_key` | 只保留原BM25排名更高者 |
| 查询与候选产品ID精确重合，另一个候选产品ID显式不相交 | 精确重合者在冲突者之前 |
| 查询与候选设施ID精确重合，另一个候选设施ID显式不相交 | 精确重合者在冲突者之前 |
| 候选没有强类型ID | 保持中性，不因缺字段被硬删除 |
| 元数据仅为`model_candidate`、未复核 | 不得用于排除、折叠或强类型冲突重排 |
| 某候选缺元数据 | 保留原始BM25相对顺序并报告覆盖缺口 |
| 输入含未来、隔离或未复核记录 | 本层不得引入；输出必须是输入子集 |
| 相同输入重复运行 | 字节级结果一致 |
| 报告知识类别 | 固定`candidate`且`fact_approval=false` |

第一阶段通过线：上述契约测试100%通过，项目全套既有测试0回归，根seal复验0错误。不得用调整标量权重挽救失败；排序键固定为“可信同信息单元排除 -> 可信历史单元折叠 -> 强类型匹配层级 -> 原始BM25排名 -> memory_id”。`information_unit_key`必须来自qrels冻结前可物化的非Gold sidecar并绑定候选payload，禁止把评分侧`information_unit_id`换名后使用。

第二阶段在独立开发元数据集物化前不评分。后续真实开发评估必须预先冻结元数据来源、覆盖率、查询上下文、指标和阈值，不能用`memory_recall_cn_holdout_v1`的4个正式错误作训练或通过证据。

## 4. 基准与对照

| 对照 | 用途 |
| --- | --- |
| 原始`CandidateMemoryIndex.recall(..., text_only_bm25)` | 唯一候选生成基线；不得修改已验证安全过滤顺序 |
| `identity`后处理 | 证明无可信元数据时结果保持原序 |
| `verified_metadata_priority_v1` | 本轮无权重候选后处理 |
| `model_candidate`元数据负控 | 证明未经复核的模型标签不能驱动硬决策 |
| future/quarantine/未验证复核哈希负控 | 证明后处理不能绕过候选资格层 |

## 5. 竞争性解释

- 合成夹具正好对应已知错误类型，100%通过不代表开放世界有效。
- 产品或设施ID可能由上游模型错误抽取；因此只有可信元数据可驱动硬排序，但可信标签的成本和覆盖率尚未验证。
- 跨机构政策、上位制度和产业链关系可能没有实体重合；把实体不相交一律当负例会漏召回，因此普通实体只作解释，不作硬冲突。
- 信息单元边界本身可能有争议，官方问答有时是独立新增信息，不能只凭同域名或同机构自动合并。
- 开发集中的人工元数据可能泄漏Gold链标签；生产元数据必须只来自文档自身、来源关系和独立复核。

## 6. 证伪条件

- 后处理输出任何不在原BM25输入短名单中的记录。
- 后处理恢复任何未来、被替代、隔离、quarantine或未验证语义复核记录。
- `model_candidate`或缺少payload绑定的元数据触发排除、折叠或强冲突降级。
- 为支持重排而修改候选记录v1/v2的历史字节、外层哈希链或已封存基准绑定代码。
- 用`chain_id`、qrels、relevance grade、judgment type、Gold relation或封存排名作为运行时特征。
- 没有强类型冲突时改变原始BM25稳定顺序，或相同输入得到不同结果。
- 报告出现`approved_fact`、`fact_approval=true`或自动关系批准。
- 任一既有安全/时间/版本测试回归，或根seal复验失败。

## 7. 未来函数与过拟合边界

- 本层只能接收已完成`as_of`资格过滤的`RecallHit`，自身不得从全库重新取文档。
- 元数据必须绑定候选payload哈希；元数据创建时间不得用于伪造历史可得性。
- 当前开发基准的`curation_documents.jsonl`、`event_nodes.jsonl`和qrels属于评分/策展侧，不得作为运行时sidecar输入；新sidecar只能从检索文档自身、公开来源父子关系或独立复核产出。
- `memory_recall_cn_holdout_v1`已经用于路线诊断，永久只读；不运行新的算法排名、不重算正式分数、不把4个错误列入测试夹具。
- 第一阶段只判断契约，不报告Recall/MRR/nDCG改善。
- 第二阶段若看过结果后新增类型或优先级，必须作为新实验重新预注册。

### 实际观察

1. 三份只读审计均完成。数据审计确认运行时只可使用正文可见字段、公开来源谱系与独立注册表产出的sidecar；`event_nodes`、qrels、curation及来源清单里的`event_family_id/category/risk_tags/selection_rationale/expected_terms/split`全部列入Gold禁用清单。代码审计确认资格过滤必须先于重排，封存runner/scorer不得修改。预注册审计补充了缺失字段中性、ID打乱和关系反向等负控方向。
2. 按预注册新增独立`verified_metadata_priority_v1`模块、候选与查询两份JSON Schema及契约测试；没有修改`candidate.py`的默认召回、封存基准、runner或scorer。
3. 模块只允许`deterministic_verified`和`human_reviewed`元数据驱动排除、折叠和强类型排序，并强制绑定验证产物哈希、候选payload或查询payload、注册表快照及`feature_known_at`。`model_candidate`、未来元数据、缺失元数据和注册表不一致均保持中性。
4. 排序只处理输入`RecallHit`：同查询信息单元排除、历史重复信息单元折叠、产品/设施精确匹配优先于显式冲突；不改BM25分数、不新增候选，报告固定`knowledge_class=candidate`、`fact_approval=false`。
5. 首次定向测试为13通过、4失败；失败发生在重排前，原因是测试夹具使用不符合既有规范的短ID`MEM-A/MEM-B`。主控只把夹具改为合法ID，没有放宽生产校验。复跑结果为17项测试和6项子测试全部通过。
6. 项目全量结果为149项测试和151项子测试全部通过；`python -m compileall -q src tests`通过；`scripts/Test-ThinkTankRepo.ps1`通过，检查196个UTF-8文本和59个JSON。
7. 根封存复验`ok=true`、错误为空，`seal_manifest.json`仍为`sha256:79733fd35e4c491d577f217ddccbdd4dc14d1d59b6f747c45c099dc9984c985e`。未运行第二次正式排名。

### 反对证据

- 本轮没有物化独立真实开发sidecar，也没有报告Recall、MRR、nDCG或Top1硬负例率；合成夹具通过不能证明开放世界有效。

- 信息单元键依赖上游确定性或人工复核，覆盖率、复核成本和边界争议尚未测量；官方问答、解读和修订不能仅凭同域名或同机构自动合并。
- 模块尚未接入默认CLI和高智能分析入口。这是刻意的安全边界，也意味着当前不存在生产收益证据。
