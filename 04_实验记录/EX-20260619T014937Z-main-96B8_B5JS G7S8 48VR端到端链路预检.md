## 1. 新手摘要

这次实验想知道：已经建好的 B5JS、G7S8、48VR 三段工具，能不能用一条命令从 dry-run JSON 走到订单-候选信号归因结果。  
我们原本预计：样例 JSON 应能通过 schema、观察和订单意图三层门禁；样例 A22/KFSQ 信号应能匹配；真实格式的旧 A22/KFSQ 文件不应错误匹配 2026-06-19 的合成订单。  
实际看到：链路输出 `status=signal_match_ready`，G7S8 三层门禁均通过，48VR 产生 2 条样例匹配，真实格式源没有误匹配。  
这说明：后续拿到真实 QMT dry-run JSON 后，可以直接运行 B5JS -> G7S8 -> 48VR 链路，而不需要手工拼接中间 CSV。  
但还不能说明：A22、KFSQ 或任何低滞后候选信号已经有效，因为本次订单仍是合成 dry-run 样例，不是真实 QMT 或成交证据。  
下一步要做：配置 `${LIVE_TRADING_ROOT}` 或在可连接 QMT 的机器上生成真实 dry-run JSON，然后用同一条链路做真实观察归因。

## 2. 研究背景

本实验属于 [[02_研究方向/RD-20260618T105950Z-main-7FY3_双池轮动真实交易微观数据低滞后研究|7FY3]]。前面已经确认，仅在日频、分钟路径或非 `R²` 拟合目标里继续搜索，容易重复负控失败；真正能降低滞后不确定性的证据应来自真实观察流、委托、成交和滑点。

B5JS 已补齐 live dry-run 单轮 JSON 落盘，G7S8 已能把 JSON 拆成门禁、订单和记录，48VR 已能把订单和候选信号关联。本次只做一件事：把这三段固定成一个端到端预检入口，减少未来真实 dry-run 数据到来后的人工操作风险。

## 3. 实验前假设

如果三段工程门禁接口已经足够稳定，那么新增链路脚本应能在一条命令中完成：

- 读取一个或多个 B5JS JSON。
- 生成 G7S8 的 `summary.json`、`dry_run_json_gate.csv`、`orders.csv`、`records.csv`。
- 在提供候选信号源时继续生成 48VR 的匹配、未匹配和信号源摘要。
- 生成总链路 `chain_summary.json`，明确区分链路实验 ID 和复用的 48VR 模块 ID。

如果假设为真，应该看到：

## 6. 竞争性解释

即使链路通过，也可能只是因为：

- 样例 A22/KFSQ 是人为构造的正控，不是真实信号收益证据。
- G7S8 输入 JSON 仍是合成样例，不代表真实 QMT dry-run、撤单、未成或成交生命周期。
- 真实格式源没有匹配，可能只是日期不重合，而不是证明候选信号不会误归因。
- 链路脚本只降低人工拼接错误，不能替代未来函数、样本外、成本、滑点或成交质量审计。

## 7. 证伪条件

出现以下情况，本假设不通过：

- 新链路脚本不能稳定生成 `g7s8/`、`48vr/` 和 `chain_summary.json`。
- 样例 JSON 不能通过 G7S8 三层门禁，或订单意图丢失。
- 样例信号不能匹配，说明 48VR 接口拼接错误。
- 真实格式 A22/KFSQ 源错误匹配合成订单，说明归因逻辑过宽。
- 单元测试或编译检查失败。
